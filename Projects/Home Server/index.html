Self-Hosted Home Server (ZimaOS)

A mini PC turned home server: zero-trust remote access, HTTPS from my own certificate authority, and self-hosted apps with nothing exposed to the internet.

Author: William Lacy  ·  Date: November 2026  ·  Environment: GMKtec mini PC running ZimaOS, NetBird Cloud, Windows 11 and iPhone clients

Summary

I turned a mini PC into a self-hosted home server that runs my password manager, a budgeting app and network file storage. I replaced the existing Kali Linux install with ZimaOS, put every web app behind a reverse proxy with certificates from my own private certificate authority, and replaced the vendor's remote-access feature with a zero-trust VPN that requires sign-in and approval for every device.

Nothing on the server is exposed to the internet. No ports are forwarded on the router, and remote access only works from devices I have enrolled and approved.

Build

1. Operating system

I flashed the ZimaOS installer to a USB drive, booted the mini PC from it, and installed to the internal SSD. The installer wipes the target disk, which removed the previous Kali Linux install completely. The server was given a fixed LAN address (192.xxx.x.xxx) and is administered from the ZimaOS web dashboard.

2. Remote access: ZeroTier replaced with NetBird

ZimaOS ships a Remote Access feature built on a public ZeroTier network. On a public network, anyone who knows the network ID is authorized automatically and can't be removed, so the only control left is the dashboard password. I replaced it with NetBird.

  • Enrollment: the server joined with a single-use, non-ephemeral setup key, which I revoked once it was enrolled. Clients sign in through an identity provider account protected by MFA.
  • Peer approval: new devices can't connect until I approve them in the dashboard.
  • Least-privilege policy: two groups, servers and my-devices, with one policy allowing my-devices → servers. The default allow-all policy is deleted, so the server can't initiate connections to my devices and unapproved peers reach nothing.
  • Network route: the server acts as the routing peer for the home subnet, so remote devices can reach LAN addresses through the tunnel.
  • Decommissioning: after NetBird was confirmed working from cellular, I turned off ZimaOS Remote Access and uninstalled the ZeroTier and Zima clients from my PC.

Normal internet traffic stays split-tunneled; only traffic to the server goes through the encrypted tunnel, peer-to-peer where possible and through an end-to-end encrypted relay otherwise.

3. HTTPS with a private certificate authority

I didn't want to buy a domain or expose anything publicly, so I ran my own CA with mkcert on my Windows PC:

  • Issued a wildcard certificate for the internal lab domain and a separate certificate for the server's VPN hostname, and uploaded both to Nginx Proxy Manager as custom certificates.
  • Installed the root CA certificate on my PC and iPhone (with full trust enabled on iOS). The CA's private key never leaves the PC.
  • Left the ZimaOS dashboard on plain HTTP internally and handled all TLS in the proxy, which avoids a port conflict between ZimaOS's gateway and the proxy on 443.

Each app has its own proxy host with Force SSL, HTTP/2, Block Common Exploits and WebSocket support enabled, and Access Lists restrict who can reach them.

4. Vaultwarden (password manager)

Vaultwarden's web vault only runs in a secure context, so it sits behind the proxy on the VPN hostname (xxx.netbird.xxx). Configuration:

DOMAIN=https://xxx.netbird.xxx
SIGNUPS_ALLOWED=false        # set after creating my account
INVITATIONS_ALLOWED=false
ADMIN_TOKEN=<admin-token>
  • Two-step login is enabled on my vault account.
  • The container's /data folder is backed up off the server.
  • I migrated my vault from Proton Pass and use the official Bitwarden clients (browser extension and iPhone) pointed at the self-hosted server.

5. Actual Budget

Actual Budget's in-browser database uses SharedArrayBuffer, which browsers only allow on HTTPS pages. I gave it its own proxy host on the wildcard certificate so it loads over trusted HTTPS.

6. Name resolution with the VPN off

The VPN hostname only resolves while NetBird is connected. So the apps keep working on my home PC with the VPN off, I added hosts-file entries mapping the app hostnames to the server's LAN address. With the VPN on, the hosts file still wins and traffic stays on the LAN.

192.xxx.x.xxx   xxx.netbird.xxx
192.xxx.x.xxx   <app>.lab.xxx

7. Network storage

I repurposed a 2 TB HDD from an old PC, shared it over SMB from ZimaOS, and mapped it as a network drive in Windows. SMB uses port 445 directly, so file access doesn't go through the web proxy.

Findings

Vendor convenience features can be the weakest link. The built-in remote access worked out of the box, but on a public ZeroTier network it reduced security to a single dashboard password. Replacing it with identity-based, approval-gated access was the biggest security gain in the project.

A reverse proxy only protects the routes that go through it. The dashboard and the proxy's admin page are still reachable directly by IP and port on the LAN, bypassing Access Lists. Closing that needs host firewall rules on the server.

Passkeys don't migrate with a vault export. Passwords moved from Proton Pass to Vaultwarden, but passkeys didn't import from the export file; they have to be re-registered per site or moved with the Credential Exchange Protocol where both apps support it.

Next Steps

  • Block direct access to the dashboard and proxy-admin ports with host firewall rules, so all web access goes through the proxy.
  • Set the proxy's default site to drop unmatched requests (444) instead of serving a page.
  • Require client certificates (mutual TLS) on the dashboard's proxy host, so only devices holding a certificate from my CA can connect.
  • Add MFA in front of the ZimaOS dashboard with forward authentication (Authelia or Keycloak), since ZimaOS has no native two-factor login.
  • Replace per-device hosts files with local DNS records served to both LAN and VPN clients.
  • Turn the spare Raspberry Pi into a hardened SSH jump host as the single admin entry point.
